## 任务提示词

以下为本题完整的 User Prompt 原文，两次执行必须使用完全相同的文本。

我们的流式计算需要保存中间状态，重启后要恢复到崩溃前的位置，不能重复也不能丢。请从零实现一个流处理的状态后端组件。仓库目前只有一个空的 Maven 工程（pom.xml 只声明 JUnit 5 与 AssertJ）。要求：1) 支持按 key 保存与读取状态，并按事件序号记录处理位点；2) 支持周期性快照：把状态与位点一起落盘，快照期间不阻塞状态更新；3) 支持恢复：从最近快照加载状态并从对应位点继续消费，需验证不重复处理已确认事件；4) 支持增量快照：只写变化过的 key，需说明与全量快照的取舍；5) 支持状态过期清理：按 key 的存活时间清理陈旧状态并统计清理量；6) 支持并发更新：多线程更新不同 key 不得互相阻塞，同一 key 的更新必须有序；7) 提供统计：状态 key 数、快照次数、恢复耗时与清理量；8) 测试覆盖状态读写、快照不阻塞、恢复不重复、增量快照、过期清理与并发更新；`mvn -q verify` 一条命令跑通。

## 设计说明

### 组件结构

| 类 | 职责 |
|----|------|
| `KeyedStateBackend` | 核心状态后端：按 key 读写状态、记录处理位点、快照/恢复、TTL 清理、周期快照调度 |
| `StateMetrics` | 统计：快照次数（全量/增量）、清理量、恢复耗时、被拒绝的重复事件数 |
| `SnapshotInfo` | 快照元数据（id、位点、条目数、是否增量、文件路径） |

### 关键语义

- **按 key 状态 + 处理位点**：`update(key, value, eventSeq)` 应用事件并维护全局位点
  （已确认事件的最大序号）。去重是**按 key** 的：事件序号不大于该 key 最近应用的
  序号（或恢复位点）时拒绝并计数，保证崩溃恢复后已确认事件不会被重复处理，
  同时不同 key 的事件序号互不影响。
- **快照不阻塞更新**：状态存于 `ConcurrentHashMap`，快照时直接对 map 做弱一致拷贝，
  再在调用线程（或后台调度线程）写盘，全程不持有任何 key 锁，写盘 IO 不阻塞
  `update`。文件先写 `.tmp` 再原子 rename，避免半截快照。
- **并发更新**：按 key 哈希分 64 个 stripe 锁。不同 key（不同 stripe）互不阻塞；
  同一 key 的更新串行执行，乱序到达的旧序号事件会被拒绝，保证同 key 有序。
- **恢复**：加载 id 最大的全量快照，再按 id 顺序重放其后的所有增量快照
  （含过期 key 的墓碑），恢复位点作为续传起点，消费端从 `position + 1` 继续。

### 全量快照 vs 增量快照的取舍

| 维度 | 全量快照 | 增量快照 |
|------|----------|----------|
| 写盘量 | 每次写全部 key，IO 与状态规模成正比 | 只写上次快照以来变化的 key（含删除墓碑），IO 与变化率成正比 |
| 快照耗时/对更新的影响 | 拷贝与序列化量大，适合低频 | 量小，适合高频周期执行 |
| 恢复速度 | 读一个文件即可，恢复最快 | 需读最近全量 + 链上全部增量，链越长恢复越慢 |
| 空间占用 | 每个快照自包含，旧快照可直接删 | 增量依赖基线全量，不能单独删除基线 |

**实践建议**：低频全量（如每小时）作为基线 + 高频增量（如每分钟）降低常态 IO；
定期用新的全量快照截断增量链，控制恢复耗时与磁盘占用。这也是 Flink
RocksDB 增量检查点的基本思路。

### 状态过期清理

每个 key 记录最近访问时间（读会刷新）。`cleanupExpired(ttlMillis)` 移除超过
TTL 未访问的 key，返回并累计清理量；被清理的 key 会标记为 dirty，使下一个
增量快照写入墓碑，保证恢复后不会"复活"。
